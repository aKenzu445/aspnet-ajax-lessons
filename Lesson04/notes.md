# Занятие 4 — заметки и выводы

## Задача 1. «Пустой» заголовок страницы

**До:** в `_Layout.cshtml` (занятие 3) уже было `<title>@ViewData["Title"] — Task Manager</title>`, но значение никто не задавал. View Page Source:
```
/      → <title> — Task Manager</title>
/Tasks → <title> — Task Manager</title>
```
`ViewData["Title"]` было `null`, и Razor вывел пустоту перед тире.

**После:** в начале страниц добавлен блок `@{ ViewData["Title"] = "..."; }`:
```
/      → <title>Главная — Task Manager</title>
/Tasks → <title>Задачи — Task Manager</title>
```
**Почему это работает:** `ViewData` — словарь (`Dictionary<string, object>`) одного запроса, общий для страницы и её layout. Страница выполняется **раньше** layout, поэтому значение, записанное в странице, layout уже видит.

## Задача 2. ViewBag и ViewData — одно и то же

**Эксперимент:** в `TasksModel.OnGet()` значение записано через **ViewData**:
```csharp
ViewData["PageDescription"] = "Здесь вы можете управлять своими задачами";
```
а в `Tasks.cshtml` прочитано через **ViewBag**:
```cshtml
<p class="page-description">@ViewBag.PageDescription</p>
```
**Результат:** на странице выведено «Здесь вы можете управлять своими задачами».

**Почему сработало:** `ViewBag` — не отдельное хранилище, а **динамическая обёртка** (`dynamic`) над тем же словарём `ViewData`. `ViewBag.PageDescription` — это просто другой синтаксис для `ViewData["PageDescription"]`. Отличия:
- `ViewData["Ключ"]` — доступ по строковому ключу, при чтении нужно приведение типа: `(string)ViewData["Title"]`;
- `ViewBag.Ключ` — короче и без приведения типа (`dynamic` проверяется только во время выполнения).
- **Оба** слабо типизированы: опечатку в ключе (`ViewData["Titel"]` или `ViewBag.Titel`) компилятор **не найдёт**, будет просто `null`.

**Что выбрать в проекте:** для мелочей (заголовок, описание) подходит любой. Достаточно договориться об одном стиле. Для структурированных данных нужна строго типизированная модель (`Model`, см. задачи 6–7).

## Задача 3. Классическая форма и паттерн Post-Redirect-Get

Форма `<form method="post">` с полем `name="title"` отправляет **POST /Tasks**. Его обрабатывает `TasksModel.OnPost(string title)`: добавляет задачу и возвращает `RedirectToPage()`.

**Что происходит по шагам (видно во вкладке Network):**
1. `POST /Tasks` → ответ **302 Found**, заголовок `Location: /Tasks`;
2. браузер сам делает **новый** `GET /Tasks`;
3. `OnGet()` заново читает хранилище, новая задача в списке.

**Визуальная разница с AJAX-формой:**

| AJAX-форма (занятие 1) | Классическая форма |
|---|---|
| Страница **не перезагружается**, обновляется только список | Страница **перезагружается целиком**, заметно «мигает» |
| Запрос: `POST /api/tasks` (JSON) → 201 | Запрос: `POST /Tasks` (данные формы) → 302 → `GET /Tasks` → 200 |
| Нужен JavaScript | Работает даже с отключённым JavaScript |

**Зачем редирект (PRG):** без него после POST браузер показал бы страницу как результат POST-запроса. Тогда нажатие F5 спросило бы «Отправить форму повторно?» и добавило бы задачу второй раз. После редиректа последний запрос — безопасный GET.

## Задача 4. TempData: флеш-сообщение после редиректа

В `OnPost` перед `RedirectToPage()` записывается `TempData["Message"] = "Задача успешно добавлена!"`, а в начале `Tasks.cshtml` выводится `@if (TempData["Message"] != null) { ... }`.

**Проверка (с сохранением cookie между запросами):**
```
POST /Tasks                 → 302 (редирект)
GET  /Tasks (после редиректа) → «Задача успешно добавлена!» ✅
GET  /Tasks (F5)              → сообщения нет ✅ (TempData «израсходован»)
```
**Почему так:** `TempData` хранится в cookie браузера до **следующего** запроса. Когда значение прочитано (`TempData["Message"]`), оно помечается на удаление и после этого запроса исчезает. Поэтому сообщение показывается ровно один раз.

## Задача 5. Классическое удаление с подтверждением через TempData

- Обработчик `OnPostDelete(int id)`. Имя `OnPost` + `Delete` = **именованный обработчик**. На одной странице может быть несколько `OnPost...`.
- Форма в каждой строке (`_TaskItem.cshtml`):
  ```cshtml
  <form method="post" asp-page="/Tasks" asp-page-handler="Delete" asp-route-id="@Model.Id">
  ```
  Тег-хелпер генерирует `action="/Tasks?id=3&handler=Delete"`: `handler=Delete` выбирает метод `OnPostDelete`, а `id=3` попадает в параметр `id`.
- После удаления: `TempData["Message"] = "Задача №3 удалена"` и `RedirectToPage()`.

**Проверка:** `POST /Tasks?id=3&handler=Delete` → 302 → страница с сообщением «Задача №3 удалена», задачи №3 в списке нет.

**Строки, добавленные через AJAX,** собираются в JS (`taskToHtml`). Чтобы их кнопка «Удалить (форма)» тоже работала, в форму подставляется анти-подделочный токен `__RequestVerificationToken`. JS берёт его из формы, которую сгенерировал Razor. Без токена сервер отклонит POST с кодом 400.

## Задача 6. Прототип /Stats через ViewBag: проблемы

Страница `Stats.cshtml` **без** `Stats.cshtml.cs`: прямо в блоке `@{ }` берётся `TaskStorage.GetAll()`, считаются числа и пишутся в `ViewBag.TotalCount / DoneCount / UndoneCount`.

Результат при 5 задачах (3 выполнены): **Всего: 5, Выполнено: 3, Не выполнено: 2** ✅

**Проблемы подхода** (записаны и в комментарии в файле):
1. **Сложно тестировать:** логика внутри `.cshtml`, её нельзя вызвать из unit-теста как метод класса.
2. **Нет проверки компилятором:** `ViewBag` — `dynamic`, опечатку в имени никто не заметит до запуска.
3. **Плохо читается:** вычисления вперемешку с HTML, через полгода трудно разобраться.

## Задача 7. Рефакторинг в строго типизированную модель + демонстрация опечатки

Логика перенесена в `StatsModel.OnGet()` со свойствами `int TotalCount, DoneCount, UndoneCount`, в `.cshtml` теперь `@Model.TotalCount`. Внешне страница не изменилась.

**Демонстрация (опечатка `TotlCount`):**

| Где опечатка | Что происходит |
|---|---|
| `@Model.TotlCount` | Проект **не компилируется**: `error CS1061: "StatsModel" не содержит определения "TotlCount"`. Rider подчёркивает красным сразу при наборе |
| `@ViewBag.TotlCount` | Компиляция **успешна** («Ошибок: 0»), а на странице `<td>Всего:</td><td></td>`: молча пусто, ошибка всплывёт только у пользователя |

**Вывод:** строго типизированная модель ловит ошибки на этапе компиляции, ViewBag — только во время выполнения (а часто и вообще никак).

## Задача 8. TempData.Keep() и TempData.Peek()

**Проверено на практике** (cookie сохраняются между запросами, как в браузере):

| Способ чтения на странице | После редиректа | F5 | ещё F5 | Ушёл на /Stats и вернулся |
|---|---|---|---|---|
| `TempData["Message"]` (обычное) | ✅ видно | ❌ пропало | — | — |
| `TempData.Peek("Message")` | ✅ видно | ✅ видно | ✅ видно | ✅ **всё ещё видно** |

**Разница:**
- `TempData["Message"]` **читает и помечает на удаление**: после этого запроса значения не станет.
- `TempData.Peek("Message")` **читает, не помечая**: значение остаётся до тех пор, пока его кто-нибудь не прочитает обычным способом.
- `TempData.Keep("Message")` снимает пометку с уже прочитанного значения, и оно доживает ещё до одного запроса.

**Когда Peek уместен:** нужно «заглянуть» в значение, не расходуя его. Например, проверить наличие сообщения в одном месте, а вывести в другом, или пережить одно лишнее обновление (вместе с `Keep`).

**Когда опасен:** для флеш-сообщений («Задача добавлена»). Пользователь видит его бесконечно при каждом обновлении и может решить, что задача добавляется снова. Поэтому в рабочем коде оставлено обычное чтение, а вариант с `Peek` сохранён в комментарии в `Tasks.cshtml`.

## Задача 9. Валидация классической формы через TempData

**Было:** классическая форма с пустым названием молча создавала задачу с пустым именем. AJAX-версию защищал код 400 (занятие 1, задача 9), а форму — нет.

**Стало:** в `OnPost(string title)` проверка `string.IsNullOrWhiteSpace(title)`. Если пусто или одни пробелы, задача **не** добавляется, пишется `TempData["Error"] = "Название задачи не может быть пустым"` и выполняется редирект. На странице ошибка выводится **красным** блоком (`alert-error`), успех — зелёным (`alert-success`).

Проверка: отправка `"   "` → 302 → «Название задачи не может быть пустым», количество задач не изменилось (3 → 3).

**Сравнение подходов:**

| | AJAX (`POST /api/tasks`) | Классическая форма (`POST /Tasks`) |
|---|---|---|
| Код ответа при ошибке | **400** + JSON `{ "error": "..." }` | **302** → `GET` → **200** (обычная страница) |
| Кто показывает ошибку | JavaScript на странице | HTML, сгенерированный сервером (TempData) |
| Перезагрузка страницы | Нет | Да |
| Когда уместно | API, интерактивные страницы, мобильные клиенты | Работа без JavaScript, простые формы |

## Задача 10. Единое правило для заголовка и описания

**Правило (применено ко всем страницам: Index, Tasks, Stats, а также About и Error):**
- `ViewData["Title"]` — **всегда в начале `.cshtml`** страницы (как в задаче 1);
- `ViewData["Description"]` — **всегда в `OnGet()`** её PageModel (как в задаче 2). Для главной ради этого создан `Index.cshtml.cs` (`IndexModel`).

`_Layout.cshtml` выводит оба значения в одном месте:
```cshtml
<h1 class="page-title">@ViewData["Title"]</h1>
<p class="page-description">@(ViewData["Description"] ?? "")</p>
```
`??` — оператор «если слева null, взять значение справа». Даже если какая-то страница забудет задать описание, вместо него будет пустая строка, а не текст `null`. Собственные `<h1>` и `ViewBag.PageDescription` со страниц убраны: теперь это делает layout.

**Проверка:**

| Страница | `<title>` | Описание |
|---|---|---|
| `/` | Главная — Task Manager | Проверка API сервера: информация, сумма, echo и деление через AJAX |
| `/Tasks` | Задачи — Task Manager | Здесь вы можете управлять своими задачами |
| `/Stats` | Статистика — Task Manager | Сколько задач всего, сколько выполнено и сколько осталось |
| `/About` | О сервере — Task Manager | Имя, версия и время работы сервера (страница без AJAX) |
