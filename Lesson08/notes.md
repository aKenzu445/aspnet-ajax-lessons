# Занятие 8 — заметки и выводы

## Задача 1. Проблемы категорий в виде строки

В проекте уже есть «быстрое» решение из прошлых домашек: `TaskItem.Category` — **строка** (`string?`, ДЗ занятия 5), плюс список допустимых значений `TaskCategories.All` и атрибут `[AllowedCategory]` (ДЗ занятия 6). Так делать **плохо**:

1. **Опечатки и разное написание.** «Работа», «работа», «Робота» для базы — три **разные** категории. Атрибут `[AllowedCategory]` частично спасал, но список зашит в код. Чтобы добавить категорию, нужно менять код и пересобирать проект.
2. **Нельзя централизованно переименовать.** Чтобы «Учёба» стала «Обучение», нужно обновить строку **в каждой** задаче (`UPDATE Tasks SET Category = ...` по всем строкам). Если что-то пропустить, данные станут несогласованными.
3. **Нет списка «все категории».** Получить его можно только перебором всех задач (`Select(t => t.Category).Distinct()`, как в фильтре ДЗ занятия 5). Категория без задач вообще «не существует», её нельзя создать заранее.
4. **Лишнее место и медленный поиск:** одна и та же строка хранится в каждой задаче, а сравнивать строки дольше, чем числа.

**Вывод:** категориям нужна **отдельная таблица** `Categories (Id, Name)` и связь «один-ко-многим» с задачами через **внешний ключ** `Tasks.CategoryId → Categories.Id`:
- имя категории хранится **один раз**. Переименование — одно изменение в одной строке;
- задача ссылается на категорию **по номеру** (`CategoryId`). База сама не даст сослаться на несуществующую категорию (ограничение внешнего ключа);
- список категорий — это просто `SELECT * FROM Categories`, и новые категории добавляются без изменения кода (страница `/Categories`, задача 4).

## Задача 2. Сущность Category и связь «один-ко-многим»

- `Models/Category.cs`: `Id`, `Name`, навигационное свойство `List<TaskItem> Tasks`.
- `TaskItem`: строковое `string? Category` (ДЗ занятий 5–6) **удалено**. Вместо него `int? CategoryId` (внешний ключ) и `Category? Category` (навигационное свойство).
- `TaskDbContext`: `public DbSet<Category> Categories => Set<Category>();`
- Связь описана **по соглашению EF Core**: имя `CategoryId` = имя навигации `Category` + `Id` ключа. Настройки через Fluent API не нужны.
- Удалены `Models/TaskCategories.cs` (список, зашитый в код) и `Validation/AllowedCategoryAttribute.cs`. Их работу теперь выполняет таблица `Categories` и **внешний ключ**: база не даст сохранить номер несуществующей категории.
- Код переведён со строки на номер: API принимает `categoryId`, фильтр — `?categoryId=2`, формы — `<select asp-for="...CategoryId" asp-items="Model.CategoryOptions">`.

Проект компилируется («Ошибок: 0»). Миграции пока нет — следующий шаг.

## Задача 3. Миграция со связью и начальными данными

- `TaskDbContext.OnModelCreating`: `modelBuilder.Entity<Category>().HasData(...)` с тремя категориями (Работа, Учёба, Личное).
- `dotnet ef migrations add AddCategories`. В сгенерированном `Up()` есть всё, что требует задание:
  - `CreateTable(name: "Categories", ...)` — новая таблица;
  - `AddColumn<int>(name: "CategoryId", table: "Tasks", nullable: true)` — столбец внешнего ключа;
  - `InsertData(table: "Categories", ...)` — три seed-строки из `HasData`;
  - `CreateIndex("IX_Tasks_CategoryId")` + `AddForeignKey("FK_Tasks_Categories_CategoryId")` — индекс и внешний ключ;
  - `DropColumn(name: "Category", table: "Tasks")` — удаление старого текстового столбца.
- **Доработка миграции вручную (сохранение данных):** EF поставил `DropColumn("Category")` **первой** операцией, и строковые категории из ДЗ занятий 5–6 пропали бы. Я перенёс `DropColumn` в конец и перед ним добавил два SQL-запроса (`migrationBuilder.Sql`): (1) добавить в `Categories` недостающие названия; (2) проставить задачам `CategoryId` по старому названию. Проверено на копии базы занятия 7:
  ```
  ДО:    1|Изучить валидацию|Спорт   5|Нормальная|Хобби   9|Корректная задача|Работа
  ПОСЛЕ: Categories: 1 Работа, 2 Учёба, 3 Личное, 4 Спорт, 5 Хобби
         Tasks: 1 → CategoryId 4 (Спорт), 5 → 5 (Хобби), 9 → 1 (Работа)
  ```
- `dotnet ef database update` (или запуск проекта). EF выдаёт **предупреждение**, что часть операций нельзя выполнить в транзакции. SQLite не умеет менять столбцы и внешние ключи «на месте», поэтому EF пересоздаёт таблицу `Tasks` (копирует данные во временную таблицу). Это ожидаемо.
- **Проверка базы:** таблица `Categories` уже содержит 3 строки, хотя в коде нет ни одного ручного INSERT, только `HasData`. В `Tasks` появился столбец `CategoryId` и внешний ключ `CategoryId → Categories.Id` (`PRAGMA foreign_key_list(Tasks)`). Столбца `Category` больше нет.

## Задача 6. «Пустая» категория в списке задач и `.Include`

**Причина (теория 8.3):** EF Core **не загружает связанные данные автоматически**. `await _db.Tasks.ToListAsync()` выполняет `SELECT ... FROM Tasks`, и у каждой задачи `task.Category == null`, хотя `CategoryId` в базе заполнен. Так сделано намеренно, чтобы не тянуть лишние данные.

**Что получилось на практике (интересный нюанс):** сначала названия категорий **показывались и без Include**. Причина: на той же странице для фильтра загружаются **все категории** (`_db.Categories.ToListAsync()`) в **тот же** `DbContext`. EF сам связывает уже отслеживаемые объекты между собой (*relationship fix-up*): задача с `CategoryId = 3` получает ссылку на загруженную категорию №3. Это «случайная» работа, на которую нельзя полагаться.

**Воспроизведение «чистой» проблемы:** временно убрал загрузку категорий для фильтра:
```
@Model.Category?.Name  → <span class="task-category"></span>   (пусто)
@Model.Category!.Name  → 500, страница «Ошибка», в консоли System.NullReferenceException
```

**Исправление:**
```csharp
IQueryable<TaskItem> query = _db.Tasks.Include(t => t.Category).AsQueryable();
```
`Include` — «жадная загрузка» (eager loading): EF делает **один** SQL-запрос с `JOIN` и заполняет `task.Category` у каждой задачи. После исправления: «Личное», «Работа» у соответствующих задач, независимо от того, что ещё загружено на странице.

**Проблема N+1 (теория 8.4):** если бы вместо `Include` в цикле для каждой задачи делался `FindAsync(task.CategoryId)`, то при 100 задачах было бы **101 запрос** к базе. С `Include` запрос один.

## Задача 7. Фильтр по категории через LINQ

- На `/Tasks` форма `method="get"` с выпадающим списком категорий (из таблицы) и кнопкой «Применить». Выбор попадает в адрес: `/Tasks?categoryId=2`.
- `OnGetAsync(int? categoryId)` → условная фильтрация:
  ```csharp
  var query = _db.Tasks.Include(t => t.Category).AsQueryable();
  if (categoryId.HasValue)
      query = query.Where(t => t.CategoryId == categoryId);
  InitialTasks = await query.ToListAsync();
  ```
  `AsQueryable()` — запрос пока **не выполнен** (отложенное выполнение), к нему можно по условию добавлять `Where`. В базу он уходит только на `ToListAsync()` одним SQL-запросом.

**Проверка:**
```
/Tasks?categoryId=2 → только «Диплом», «Конспект» (категория «Учёба»), в фильтре выбрано «Учёба»
/Tasks              → все 6 задач
```
(Фильтр по строке существовал ещё с ДЗ занятия 5. Здесь он переведён на `CategoryId` и `Include`.)

## Задача 8. Группировка и агрегация для статистики

`StatsModel.OnGetAsync`:
```csharp
var byCategory = await _db.Tasks
    .GroupBy(t => t.Category!.Name)                                   // SQL: GROUP BY Categories.Name
    .Select(g => new { CategoryName = g.Key, Count = g.Count() })    // SQL: COUNT(*)
    .OrderByDescending(x => x.Count)
    .ToListAsync();
```
Для задач без категории ключ группы — `null`, на странице «Без категории».

**Проверка:**
```
Всего: 7
Учёба: 2, Личное: 2, Спорт: 1, Работа: 1, Без категории: 1
Итого по категориям: 7   ← совпадает с «Всего» (занятие 4)
```

**Ошибка по ходу:** сначала проекция была сразу в `record CategoryStat(...)`, а затем `.OrderByDescending(x => x.Count)`. EF Core выдал `InvalidOperationException: The LINQ expression ... could not be translated`: он не умеет перевести в SQL сортировку по свойству объекта, созданного конструктором. Исправление: проекция в **анонимный объект** (как в задании), сортировка и `ToListAsync()` в базе, а преобразование в `CategoryStat` — уже **в памяти**. Важный вывод: не любое C#-выражение в LINQ-запросе к базе EF может превратить в SQL.
