# Занятие 2 — заметки и выводы (то, что нужно «зафиксировать письменно»)

## Задача 1. Диагностика: сервер «не глухой», но мы этого не видим

**Что сделано:** запустил проект и выполнил 4 запроса через страницу: открыл `/`, загрузил `/api/tasks`, посчитал сумму `/api/sum?a=1&b=2`, разделил на ноль `/api/divide?a=1&b=0`.

**Что вывела консоль сервера** (вкладка Run в Rider):

```
info: Microsoft.Hosting.Lifetime[14]
      Now listening on: http://localhost:5102
info: Microsoft.Hosting.Lifetime[0]
      Application started. Press Ctrl+C to shut down.
info: Microsoft.Hosting.Lifetime[0]
      Hosting environment: Development
info: Microsoft.Hosting.Lifetime[0]
      Content root path: .../Lesson02
```

**Вывод:** консоль показывает только сообщения о **запуске** сервера. Ни одного слова о том, **какие запросы пришли**, от кого, с каким результатом. Запросы обработаны (на странице ответы есть), но разработчик этого не видит. В продакшене так нельзя: без логов невозможно разобраться в ошибках и в нагрузке. Решение — собственный middleware логирования (задачи 2–3).

## Задача 5. Route constraint: защита от некорректного типа параметра

**До исправления** (маршрут `/api/tasks/{id}`, обработчик с параметром `int id`):

```
GET /api/tasks/abc → 400 Bad Request
Microsoft.AspNetCore.Http.BadHttpRequestException: Failed to bind parameter "int id" from "abc".
```

Маршрут **подошёл** (`{id}` принимает любой текст), ASP.NET Core попытался превратить `"abc"` в `int`, не смог и выбросил исключение. В режиме Development клиент получает «страшный» текст исключения со стеком вызовов. Наш код не выполнился, но ответ некрасивый и раскрывает внутренности сервера.

**После исправления** (маршрут `/api/tasks/{id:int}`):

```
GET /api/tasks/abc → 404 Not Found (пустой ответ: маршрут не найден)
GET /api/tasks/1   → 200 {"id":1,"title":"Изучить ASP.NET","isDone":false}
GET /api/tasks/99  → 404 {"error":"Задача не найдена"} (это уже наш код)
```

**Вывод:** ограничение `:int` проверяется на этапе **маршрутизации**. Если `id` не целое число, маршрут просто «не подходит», и сервер отвечает 404 ещё **до** входа в наш обработчик, без всякой ручной проверки. То же ограничение добавлено к `DELETE` и `PUT /api/tasks/{id:int}`.

## Задача 6. Эксперимент с порядком middleware

**Что сделано:** middleware логирования временно перенесён **после** всех `app.MapGet/MapPost/...`, прямо перед `app.Run()`. Затем выполнены запросы: `/index.html`, `/css/site.css`, `/api/tasks`, `/api/divide?a=1&b=0`, `/api/nope`.

**Консоль при логировании ПОСЛЕ Map*:**
```
[23:13:50] → GET /api/tasks
[23:13:50] ← 200 (0 ms)
[23:13:50] → GET /api/divide?a=1&b=0
[23:13:50] ← 400 (1 ms)
[23:13:50] → GET /api/nope
[23:13:50] ← 404 (0 ms)
```
Запросы к **статическим файлам** (`/index.html`, `/css/site.css`) **пропали из лога**, хотя браузер их получил (200).

**Почему так:**
- `UseStaticFiles()` теперь стоит в конвейере **раньше** логирования. Когда он находит файл в `wwwroot`, он сам отдаёт ответ и **не вызывает `next()`** (short-circuit, «короткое замыкание»). Запрос до логирования просто не доходит.
- Запросы к API в лог всё ещё попадают. `MapGet/MapPost` не добавляют middleware в конвейер в этом месте, они только **регистрируют маршруты**. Сами endpoints выполняются в самом **конце** конвейера (WebApplication автоматически ставит `UseRouting` в начало и выполнение endpoints в конец). Поэтому `app.Use(...)`, написанный после `MapGet`, всё равно срабатывает **до** выполнения endpoint'а.

**Вывод:** порядок регистрации middleware в `Program.cs` = порядок их выполнения. Middleware видит только те запросы, которые до него **дошли**. Любой middleware раньше него может «перехватить» запрос и не пустить дальше. Поэтому логирование и обработку ошибок ставят **первыми**, а проверку ключа — **до** endpoints. После эксперимента логирование возвращено в начало конвейера.

## Задача 7. Где и как применяется проверка API-ключа (обоснование выбора)

Выбран вариант **отдельный класс `ApiKeyMiddleware`** (способ 2 из теории), а не `MapGroup(...).AddEndpointFilter(...)`:
- задание прямо просит класс «по образцу способа 2»;
- middleware проверяет запрос **до** маршрутизации и endpoints, в одном месте. Любой новый изменяющий endpoint под `/api/tasks` автоматически защищён;
- проверка внутри: `Path.StartsWithSegments("/api/tasks")` и метод `POST`, `PUT` или `DELETE`.

**Почему проверяется ещё и `PUT`:** он появился в домашнем задании занятия 1 и тоже **изменяет** данные (отметка «выполнено»). Без проверки его можно было бы вызвать без ключа, а смысл задачи — защитить все изменяющие операции.

**Почему `GET` открыт:** чтение задач не изменяет данные, по условию оно доступно всем.

Проверка: `POST /api/tasks` без заголовка → **401**, с `X-Api-Key: lesson2-secret` → **201**, `GET /api/tasks` без заголовка → **200**.

## Задача 9. Рефакторинг в MapGroup

Все endpoints задач собраны в `var tasksApi = app.MapGroup("/api/tasks")`. Внутри группы пути короткие: `"/"`, `"/{id:int}"`. Итоговые URL **не изменились**, поэтому `index.html` не правился вообще. Все тесты задач 4, 7, 8 повторно проходят: GET 1 → 200, GET abc → 404, GET 99 → 404, POST без ключа → 401, POST с ключом → 201, crash-test → 500 JSON.

## Задача 10. Режим техработ

Middleware стоит после логирования и после `UseStaticFiles`, но до `UseRouting()`:

| Запрос | Без заголовка | С `X-Maintenance: true` |
|---|---|---|
| `GET /api/tasks` | 200 | **503** |
| `GET /api/sum?a=1&b=2` | 200 | **503** |
| `GET /api/hello` | 200 | **503** |
| `GET /index.html` | 200 | 200 (статика не блокируется) |
| `GET /css/site.css` | 200 | 200 |

**Вывод (главная ценность middleware):** один middleware блокирует **все** endpoints сразу, при этом код ни одного endpoint'а не менялся.

## Итоговый порядок конвейера (Program.cs)

```
1. Обработка ошибок (try/catch → 500 JSON)     ← первым, чтобы поймать ошибку где угодно
2. Логирование (→ запрос, ← код и время)        ← до статики, чтобы видеть все запросы
3. UseDefaultFiles + UseStaticFiles             ← файлы из wwwroot отдаются здесь
4. Режим техработ (X-Maintenance → 503)
5. Ограничение частоты (ДЗ, > 5 за 10 с → 429)
6. UseRouting                                   ← выбор endpoint по адресу
7. ApiKeyMiddleware (POST/PUT/DELETE → 401 без ключа)
8. Endpoints (MapGet / MapPost / MapGroup ...)
```

## Домашнее задание. Rate limiting

- Класс `Middleware/RateLimitingMiddleware.cs`. Хранилище — `Dictionary<string, List<DateTime>>`: ключ — IP-адрес, значение — время его запросов.
- При каждом запросе удаляются записи старше 10 секунд. Если осталось 5 и больше → **429 Too Many Requests**.
- `lock` защищает словарь: запросы обрабатываются параллельно, а `Dictionary` и `List` нельзя менять из нескольких потоков одновременно.
- Лимит применяется к `/api/*`. Статические файлы отдаются раньше и не считаются.
- Проверка: 7 быстрых запросов → `200 200 200 200 200 429 429`. Через 10 секунд снова 200.
